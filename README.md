# OnShop

Persian-first (RTL), multilingual online shop that runs as an installable PWA.

```
storefront/  Next.js 16 + TypeScript + Tailwind + next-intl   (customer site, fa/en)  :3000
admin/       React 18 + TypeScript + Vite + Ant Design         (WordPress-style dashboard) :5173
api/         .NET 8 Web API + EF Core + PostgreSQL + Identity/JWT                       :5080
```

> **Status: written but never compiled.** The code was authored on a machine without .NET/Node.
> Expect a few small compile/type errors on the first build. Follow "First run" below and fix what the
> compilers report; nothing is architecturally speculative.

## Everything is local (no CDN, no remote services)

- **Fonts:** Vazirmatn via the `@fontsource-variable/vazirmatn` npm package, bundled into the build.
  No Google Fonts. Icons come from `@ant-design/icons` (bundled) or inline SVG.
- **Images/uploads:** stored on local disk (`api/src/OnShop.Api/uploads`), served by the API at `/uploads`.
  The API only accepts `/uploads/...` URLs for product images.
- **Service workers:** hand-written (`storefront/public/sw.js`, `admin/public/sw.js`); no Workbox/CDN.
- **Content-Security-Policy:** production builds of both front ends set `default-src 'self'`, which makes
  the browser *refuse* any remote script, font, image or connection. If something tries to load from the
  internet, it will show up as a CSP error instead of silently working.
- **Services:** PostgreSQL only (Docker Compose or native). Redis/Meilisearch are deferred.
- **Calendar/digits:** Jalali dates and Persian digits use the browser's built-in `Intl` (no libraries).
- **Payments:** a gateway is remote by nature. It sits behind `IPaymentGateway`; today only a local
  `FakePaymentGateway` exists (refused in Production).
- The only internet access needed is the one-time `npm install` / `dotnet restore`. To work fully offline
  afterwards, keep `node_modules/` and `~/.nuget/packages` (or set up an offline mirror).

## Prerequisites

- .NET SDK 8
- Node.js 20+ (LTS)
- PostgreSQL 16+ (or Docker Desktop)

## First run

1. **Database**
   ```bash
   docker compose up -d
   ```
   Without Docker, create the same DB natively:
   `CREATE USER onshop WITH PASSWORD 'onshop_dev'; CREATE DATABASE onshop OWNER onshop;`

2. **API** (dev settings live in `appsettings.Development.json`)
   ```bash
   cd api
   dotnet restore
   dotnet run --project src/OnShop.Api
   ```
   On start it creates the schema, roles, an admin user and 4 sample products (Development only).
   - Admin login: `admin` / `Admin@12345` (change in `appsettings.Development.json` → `Seed`)
   - Health: http://localhost:5080/health

   Optional, to use real EF migrations instead of `EnsureCreated`:
   ```bash
   dotnet tool install --global dotnet-ef
   dotnet ef migrations add Initial -p src/OnShop.Infrastructure -s src/OnShop.Api -o Persistence/Migrations
   ```
   (After that the app runs `Migrate()` automatically.)

3. **Storefront**
   ```bash
   cd storefront
   npm install
   copy .env.example .env.local
   npm run dev          # http://localhost:3000  (→ /fa, /en)
   ```

4. **Admin**
   ```bash
   cd admin
   npm install
   npm run dev          # http://localhost:5173
   ```

5. **Try the flow:** add a product to the cart on the storefront → checkout → the fake gateway
   completes instantly → order page shows "paid" → open the admin → Orders / Dashboard.

### Testing the PWA
Service workers only run on production builds and need `localhost` or HTTPS:
```bash
cd storefront && npm run build && npm start
cd admin && npm run build && npm run preview
```
Then use Chrome DevTools → Application → Manifest / Service Workers, and the install button.
Icons are generated by `tools/make-icons.ps1` (already run).

## Storefront design and cart (version 3)

The storefront is styled like a supermarket site: delivery strip, main bar with a wide search field and cart total,
a categories bar with an "All categories" menu, flat cards with thin borders, green/orange palette, red discount
badges, category tiles, a multi-column footer. Colors live in `storefront/tailwind.config.ts` (`brand`, `accent`) and the
shared button/card/input styles in `storefront/src/app/globals.css`.

Adding to the cart has no flying animation. The "Add" button turns into a − / quantity / + stepper in place, the header
cart shows the running total, the cart opens as a slide-in **mini cart** (also on the mobile bottom bar), and only the
count badge gives a tiny bump when it changes.

## Testing on a phone

Open the storefront from the phone at `http://<PC-ip>:3000` (the dev server prints it as "Network"). Both devices must be on
the same network and the Windows firewall must allow Node on port 3000.
- Storefront: Next.js 16 blocks dev scripts for non-localhost hostnames, so without `allowedDevOrigins` the page looks fine
  but **no button works** (it never hydrates). `next.config.ts` allows the usual private ranges (192.168.*.*, 10.*.*.*,
  172.*.*.*); add others with `DEV_ORIGINS="my-pc.local"`. Restart `npm run dev` after changing it. A production build
  (`npm run build && npm start`) has no such restriction.
- Admin (Vite) only listens on localhost by default: run `npm run dev -- --host`.
- Camera/GPS features such as "use my location" and the install-as-app prompt need HTTPS (or localhost) on phones;
  plain `http://<ip>` will not offer them.

## Next.js 16 notes

The storefront targets Next.js 16 (Turbopack) and next-intl 4. Locale routing runs in `src/proxy.ts` (Next 16's name for
`middleware.ts`). `next.config.ts` wires next-intl by aliasing `next-intl/config` itself instead of using
`next-intl/plugin`, because the plugin loads the `@swc/core` native addon (only needed for next-intl's optional message
extraction), which fails its permission check on some Windows machines. If `@swc/core` works on your machine you may
switch back to the plugin (snippet in the comment inside `next.config.ts`).

## Stories, recommendations, assistant, 3D store (version 4)

- **Stories** (Admin → Content → Stories): circles at the top of the home page; each story has slides (image or text
  on a flat color), a link, a duration (3-15 s) and an optional expiry date. The viewer pauses on press, tap the start
  third to go back, the rest to go forward (mirrors in RTL); seen stories lose their orange ring.
- **Recommendations** (`GET /api/recommendations`): *buy again* and *for you* use the logged-in customer's order history
  (items bought together by other customers, then best sellers in the same categories) plus the cart and favorites;
  *popular* is the fallback for guests. Pure SQL on your own database; no data leaves the server. It improves as orders
  accumulate; with no orders it shows the newest products.
- **Assistant** (`POST /api/assistant`): a local, **rule-based** helper (keywords in Persian/English: product search,
  deals, suggestions, order status for logged-in users, delivery/payment/support). It is *not* a language model. To use
  one (for example a local Ollama), implement `IAssistantBrain` and register it in `Program.cs` instead of `RuleBasedAssistant`.
- **3D store** (`/fa/shop3d`): three.js (bundled from npm) with one shelf per top-level category; drag to rotate, scroll
  to zoom, click a product to see its price and add it to the cart. Product pictures are drawn on the box fronts.
  Falls back to a link to the normal list when WebGL is unavailable. Up to 8 aisles x 12 products.
- Admin → Settings → **Store features** switches the 3D store and the assistant on or off.
- **3D store access and time limit** (Settings → Store features): *login required* (default on; guests see a sign-in
  card) and *daily minutes* (default 10, 0 = unlimited). The time is counted on the server per user per day (Tehran
  time, resets at midnight): the page calls `POST /api/me/shop3d/start` and a heartbeat every 10 s while the tab is
  visible; the server adds the clock time between beats (capped), so tabs don't double count. When time runs out the store
  is replaced by a "come back tomorrow" card. Note: the 3D page only *displays* catalog data that is public anyway, so
  the limit is a usage rule (enforced by the server's counter and the page), not a security boundary. If the admin lets
  guests in, guests are not limited.
- **Shop logo** (Settings → Site information): upload an image; it replaces the letter badge in the header, appears in
  the footer, and on the back-wall sign of the 3D store. Local uploads only. (PWA home-screen icons are separate files:
  regenerate `tools/make-icons.ps1` or replace `public/icons/*` to brand them.)
- **Trolley driving (version 5):** you push a shopping trolley that mirrors the real cart (items appear inside; look down
  to see them; wheels spin; items drop in when added). W/S drive, A/D or the arrows steer, the trolley has inertia and
  its long front end collides with shelves. Dragging turns the *head*, not the trolley (it keeps its heading; the view
  re-centers while you drive forward; C re-centers it). Click the floor/minimap and the trolley drives there on its own
  through the corridors.
- **Offers wall:** the poster's rows are clickable; a click selects that product (card with the add-to-cart control).
- **Checkout inside the store:** clicking the counter (or the Checkout button in the trolley bar) drives to the counter
  and opens the real checkout form, with editable item quantities, in an overlay. Only the payment-gateway redirect
  leaves the page (fullscreen is exited first so the map prompt and payment page work).
- **Guides:** a 6-step interactive tour (first visit, reopen with the "Help" button) that drives the trolley to the offers
  wall and the counter while it explains them, plus a contextual tip line. The tour never blocks the controls.
- **Phone mode (version 6):** full-window "immersive" layout by default (CSS, so it works on iPhone too; ✕ leaves it),
  touch **joystick** to drive, **pinch to zoom** (also +/− buttons, mouse wheel and the +/- keys on desktop), tap the floor
  to be driven there, taps near a product pick it (fat-finger tolerance), and a bottom **dock**: *Aisles* (product grid of
  the aisle you are in, each with add-to-cart and "show in store"), *Search*, *Offers*, *Map* (big tap-to-drive map) and
  *More* (counter, help, sound, quality, list view). The selected product opens as a bottom sheet. The pixel ratio is
  capped on phones (use "Low quality" on slow devices).
- 3D polish: fake contact shadows, a "special offers" poster built from the current discounts, fullscreen, and an optional
  chime (synthesized in the browser, no audio files) when an item goes into the basket.

## Delivery address on the map

Admin → **Settings → Delivery address on the map (OpenStreetMap)**: switch it on/off, choose the map center and zoom.
When on, first-time visitors are asked to pin their delivery point (they may choose "later"); the point is shown in the
header strip, prefilled at checkout, saved with the order (visible to staff in the order drawer with an OSM link) and
can be stored with saved addresses. When off, no map is shown anywhere.

**Local-only note:** Leaflet is bundled from npm, but the map *tile images* come from a tile server. The default is the
public OSM server (`tile.openstreetmap.org`), which is a remote resource and subject to OSM's usage policy (fine for a
small shop, not for heavy traffic). It is the only remote origin the storefront allows (via `MAP_TILE_ORIGIN` in the
Content-Security-Policy). To run fully local, host your own tile server, set its URL in the admin settings and set
`MAP_TILE_ORIGIN` to its origin (see `storefront/.env.example`). The map shows OSM attribution as its license requires.

## Upgrading an existing dev database (IMPORTANT)

Version 2 added tables (pages, sliders, banners, texts, addresses, favorites) and a column
(`ProductTranslations.SearchText`); version 3 added `Categories.ImageUrl`, `Orders.Lat/Lng` and `Addresses.Lat/Lng`; version 4 added the `Stories` and `StoryItems` tables.
Without EF migrations the app cannot alter an existing database, so
**the first run after updating needs a reset** (dev data is only the sample data, now grocery items):

1. In `api/src/OnShop.Api/appsettings.Development.json` set `"Database": { "RecreateOnStart": true }`
2. Run the API once, then set it back to `false`.

The API tells you this in its error message if it detects an old schema. To avoid resets in the future,
generate real migrations (see "Optional" above) once the schema settles.

## Roles, users and permissions

- Permissions are defined in `api/src/OnShop.Domain/Permissions.cs` (products, categories, orders, media,
  content, users, roles, settings, dashboard). Roles are sets of permissions; a user can have several roles.
- `Admin` always has every permission (synced at startup). `Manager` starts with catalog/orders/content/media.
  Create more roles in the admin under **Users → Roles and permissions**.
- Permissions are loaded from the database on each request (cached ~20 s), so editing a role or disabling
  a user applies almost immediately, without forcing a re-login.
- Guards: nobody can grant permissions they don't hold, edit users above their own level, disable/delete
  themselves, or remove the last active Admin.
- To add a permission: add it to `Permissions.All`, use `[Authorize(Policy = Permissions.X)]` on the endpoint,
  and use `can('x')` / `<Guard perm="x">` in the admin.

## Content: pages, blocks, sliders, banners, texts

Admin → **Content**. Create reusable **sliders**, **banners** and **fixed texts**, then build **pages** from
ordered blocks: slider, banner, text, products (by category, sort, limit) and categories list.
The page marked *home* replaces the default storefront home; other pages are served at `/p/<slug>`.
A fixed text with key `footer` is shown in the storefront footer. Images must be uploaded to the local
media library (no remote URLs).

## Search and filters

- Search matches every word against name, description, SKU and category; Persian/Arabic letter and digit
  variants and ZWNJ are normalized (`تیشرت` finds `تی‌شرت`). Results are ranked (exact > starts-with > contains).
- With the PostgreSQL `pg_trgm` extension (enabled automatically if permitted) typos are tolerated and the
  shop says so. Without it, search still works but without typo tolerance.
- The header search box shows live suggestions (products and categories).
- The shop page filters in place: category tree with live counts, price range slider, in-stock/on-sale
  toggles, sorting, active-filter chips, "load more". Counts are recomputed for the current filters.

## Customer account, favorites, compare

`/account`: profile and password, orders (with items and payment reference), payments, saved addresses
(prefilled at checkout), favorites. Favorites are kept locally for guests and merged into the account at login.
Compare (up to 4 products) has a differences-only view. Adding to cart plays a fly-to-cart animation
(disabled for users who prefer reduced motion). The footer stays at the bottom on short pages.

## What's implemented

**API:** Identity + JWT (login by username/email/phone, lockout), roles Admin/Manager/Customer,
translated catalog (products + categories, per-language slugs), search (ILIKE, digit/letter
normalization), checkout with server-side pricing and atomic stock decrement, payment gateway
abstraction, media upload with signature check, settings, dashboard stats.

**Storefront:** fa (RTL, default) + en, Jalali dates, Persian digits, product list/filter/sort/paging,
product page with SEO metadata + JSON-LD + hreflang alternates, cart (persisted), checkout, order status
page, PWA manifest + offline page + install button.

**Admin:** login, dashboard (sales chart, low stock, recent orders), products (translated fa/en tabs,
images, SEO fields), categories, orders (status workflow), media library, settings.

## Production notes
- Set `Jwt__Key` (32+ chars), `ConnectionStrings__Default`, `Payment__Gateway`, `Seed__AdminPassword`,
  `Api__PublicBaseUrl`, `Storefront__BaseUrl` via environment variables. The API refuses to start with a
  missing/short JWT key or the Fake gateway in Production.
- Serve storefront and admin behind one reverse proxy with HTTPS (needed for PWA install).
  The admin expects `/api` and `/uploads` on its own origin (Vite proxies them in dev).
- Store pages are rendered dynamically with cached API fetches (`revalidate: 30`) so builds don't need the API running.
